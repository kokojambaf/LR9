### 2 Выполнение заданий

Все задания выполнены в одном решении `UserOptimizationExample` (.NET 8, C#).
Файлы:
- `CodeOptimization.cs` – задания 5.1–5.3 (файлы, вычисления);
- `UserOptimizationExample.cs` – задания 5.4–5.8 (работа с БД через EF Core).

#### 5.1 Оптимизация чтения из файла
**Было:** синхронный `StreamReader` с буфером по умолчанию, `ReadLine()`.
**Стало:** `new StreamReader(filePath, Encoding.UTF8, true, bufferSize: 8192)` и `await reader.ReadLineAsync()`.
Поток не блокируется на ожидании диска, число обращений к ОС уменьшается за счёт большего буфера.

#### 5.2 Оптимизация записи в файл
**Было:** запись посимвольно (`foreach (char c in data) writer.Write(c)`), буфер по умолчанию.
**Стало:** `new StreamWriter(filePath, true, Encoding.UTF8, bufferSize: 8192)` и одна операция `await writer.WriteLineAsync(data)` – вместо N вызовов один.

#### 5.3 Оптимизация вычислений
**Было:** рекурсивный Fibonacci с экспоненциальной сложностью O(2ⁿ) – каждое значение вычислялось многократно.
**Стало:** поле `Dictionary<int, long> _fibonacciCache`; перед вычислением проверяется `TryGetValue`, результат сохраняется в словарь (мемоизация). Сложность O(n). `Fib(90)` вычисляется мгновенно.

#### 5.4 GetActiveUsersAsync
Добавлен `.AsNoTracking()` – EF Core не создаёт записи в ChangeTracker для сущностей, которые только читаются. После вызова `ChangeTracker.Entries().Count() == 0`.

#### 5.5 GetUsersWithOrdersAsync
Вместо `.Include(u => u.Orders)` (загрузка всех заказов целиком) используется проекция:
```csharp
.Select(u => new UserOrdersInfo(u.Name, u.Orders.Count))
```
Из БД выбираются только имя и число заказов, `COUNT` выполняется на стороне SQL.

#### 5.6 AddUsersAsync – AddRange
Вместо цикла с `SaveChangesAsync` на каждого пользователя (N round-trip к БД) – `_context.Users.AddRange(users)` и один `SaveChangesAsync()`.

#### 5.7 AddUsersAsync – транзакция
Работа с БД обёрнута в `using (var transaction = await _context.Database.BeginTransactionAsync())`, при успехе – `CommitAsync()`, при `DbUpdateException` – `RollbackAsync()` и `ChangeTracker.Clear()`.

Для проверки использован SQLite in-memory (провайдер `InMemory` не поддерживает реальные транзакции и ограничения). Введены ограничения `NOT NULL` на Name/Email и `UNIQUE` на Email.

Результаты проверки:

| Входные данные | Результат |
|---|---|
| Корректные (Alice, Bob, Charlie) | Сохранены все 3 пользователя |
| Некорректные (Name = null) | `NOT NULL constraint failed`, транзакция отменена, в БД по-прежнему 3 |
| Корректные (Diana, Eve), затем некорректные (дубликат Email) | `UNIQUE constraint failed`, откат **всей** транзакции – Diana и Eve тоже не сохранены, в БД 3 |

Транзакция обеспечивает атомарность: либо сохраняются все записи, либо ни одной.

#### 5.8 Кэширование
В `UserService` добавлены:
```csharp
private readonly TimeSpan _cacheDuration = TimeSpan.FromMinutes(5);

public async Task<List<User>> GetCachedActiveUsersAsync()
{
    if (!_cache.TryGetValue("ActiveUsers", out List<User> users))
    {
        users = await GetActiveUsersAsync();
        _cache.Set("ActiveUsers", users, _cacheDuration);
    }
    return users;
}
```
Тест: первый вызов идёт в БД, второй и третий берут данные из кэша.
